### The calibration bug our own hosting introduced

This is the part worth reading.

`Desk` seeds `random.Random(profile.name)`, so every fresh instance replays one
identical sequence. On a laptop that is fine: one long-lived process, and the
sequence advances across filings — which is what the calibrated rates
describe. **A microVM rewinds to roll one on every cold start.**

Deployed, that meant `vendor` and `payments` refused the *first* filing on a
pretext **every single time** — four probes, four identical refusals, where
chance would have made that a 0.24% event. Their published
`reject_malformed_rate` of 0.08 and 0.03 had quietly become **1.0 for the only
filing that matters.** Every calibrated rate in the lane was affected the same
way; those two are simply where the first roll happens to land on a refusal.

This was my bug, in my file. `institutions/desk_store.py` exists precisely so
desk state outlives the microVM, and I did not notice that **the RNG position
is state.** It now checkpoints alongside the tickets, the idempotency map and
the counter. Alakshendra's calibration logic is untouched.

Proven end to end rather than asserted. Before the fix, the rows carried no
`rng` attribute and both desks refused. After: first call still refuses (no
position checkpointed yet), and the second returns `VENDOR-100001` and
`PAYMENTS-100001` because the sequence now resumes instead of replaying.

**Kartik:** this is the one to know about for the tau sweep and any rate you
quote. A rate measured against the deployed desks before today was measuring
the first roll repeatedly, not the distribution.

## What the code review changed

`/code-review` returned 14 findings on this branch. The ones worth knowing:

**Two microVMs could issue the same ticket number.** `act()` did a
load-modify-write of one shared item per tool call, and AgentCore gives
concurrent filings separate microVMs. Both read `n=5`, both minted
`<DESK>-100006`, and the later `put_item` erased the earlier ticket — two
households holding one reference, one complaint gone from the desk's records.
That is hard rule 5. `save()` is now a conditional write on a `version`
attribute, and `act()` answers a refusal by reloading and re-running. Safe
because `accept()` checks its idempotency key **before** any random draw, so
the loser of a race gets the winner's number back as DUPLICATE.

**A corrupt checkpoint would have killed a desk.** `_restore_rng` caught
`TypeError` and `ValueError`, but `setstate()` raises `OverflowError` for a
negative or oversized word — so a truncated row would have propagated out and
stopped the desk answering anything until someone deleted the row, exactly
contradicting the docstring promising it would still answer.

**The deploy script opened a trap while closing five.** `agentcore configure`
rewrites `default_agent` in `.bedrock_agentcore.yaml`, so after a desk deploy
the next `agentcore` command typed without `--agent` targets a desk instead of
the main runtime. It was left pointing at `panchayat_desk_payments`. The script
now restores it, and the live file is back to `panchayat`. **That file is
gitignored, so nothing would have warned you.**

**A documentation claim I had to withdraw.** I wrote that the deploy script
means the Gemini key "never reaches a command line or a log". That is false —
it is passed to `agentcore launch` as an `-env` argument, so it sits in that
child process's argument vector and in PowerShell script-block logs. It is
protection against *committing* the key, not against a local observer. Corrected
in both the script header and SETUP.md, because a false guarantee is the reason
nobody thinks to rotate.

**And then the fix took all five desks down.** Worth writing down, because the
lesson is about the test and not the code. The conditional write treated "row
exists but has no `version`" as "no row at all", so it conditioned on the row
not existing — against rows that plainly did. Every save raised `Contended`,
`act()` retried three times and re-raised, and all five desks answered nothing.
The smoke test caught it within a minute of the deploy finishing.

**The offline fake had agreed with the bug.** It re-derived the rule from
version arithmetic instead of evaluating the condition `save()` actually
passed, so it agreed with whatever `save()` believed and could not see the one
state that mattered. It now evaluates the real boto3 condition object against
its stored item, which fails the way the deployed desks did. A fake that
re-derives the rule tests only that the code agrees with itself.

A second, quieter one from the same change: PowerShell 5.1's `Set-Content
-Encoding utf8` writes a **BOM**, and a BOM lands inside the first YAML key, so
`default_agent` would have parsed as `\ufeffdefault_agent` and `agentcore`
would have silently stopped seeing the setting the restore exists to protect.
The file is written BOM-free now and the stray BOM is stripped.

**Deferred, with reason.** The reviewer is right that `desk_store` now reaches
into three privates of `Desk` (`_by_key`, `_n`, `_rng`) and that the real fix is
a `checkpoint()`/`restore()` pair on `Desk` itself — so the next attribute added
persists automatically instead of silently failing to survive a cold start the
way `_rng` just did. That is Alakshendra's class and a cross-lane design change,
so it wants a conversation rather than a unilateral edit.

## The case page never showed the ticket arrive — fixed by Raghav, deployed by Ali

**Resolved 14 Sep.** Raghav shipped the fix in PR #43 (`7d349e6`), and it is
better than the sketch below: a `setTimeout` chain so a slow cold start cannot
stack requests, a stale-response guard, tier-4 RTIs excluded because they are
never filed, and a stop when the desk refuses. The same PR fixed a real
Watchdog bug (`f3d35e0`): a failed send left the case at ESCALATING and the
next retry drafted tier 2 over an office that never received tier 1.

**Both were merged and running nowhere** — his machine has no AWS
credentials, and there was no written path from "merged" to "deployed" for
these Lambdas. Deployed 14 Sep 09:16–09:18 UTC and proven: the served bundle
carries the new strings, and a fresh filing through the new Watchdog came back
`BWSSB-100005`. `scripts/deploy_lambdas.sh` now exists so this cannot recur.

The original analysis is kept below because the *why* is still the reference.

**The data is live; the view is a snapshot.** Verified on 14 Sep against the
deployed site, not reasoned about: a signed case reached a real ticket, but the
page sitting open on it would never have shown that.

### What a viewer sees

Sign a draft on `/live/<case_id>`. The page reloads once, then shows State
`drafted`, Submitted `— not yet —`, Ticket `— none issued —`, and **stays that
way.** The payoff only appears after clicking "Read it again". In a demo that
is the worst possible moment to go quiet: the judge has just watched you sign
and nothing happens.

### Why

`approve` records the signature and returns. **The filing happens afterwards,
asynchronously** — the signature books a Watchdog wake, the Watchdog files over
A2A, and the desk issues the reference. Measured on `case_c46daf05df50`:

| Event | Time (UTC) |
|---|---|
| Signed | 20:48:15 |
| Submitted, ticket `BWSSB-100004` | 20:49:55 |

About **100 seconds**, most of it an AgentCore cold start plus a model call.
The page never asks again in that window:

- `CaseFile` loads once on mount — `web/src/routes/Live.jsx:158-160`.
- `sign()` reloads once, immediately after `approve` resolves (`Live.jsx:165-166`)
  — which is *before* the Watchdog has done anything, so it reads the same
  unsigned-to-signed state and no ticket.
- "Read it again" (`Live.jsx:264`) is the only other reload.
- `MyCases` also loads once (`Live.jsx:95-103`), and `web/src/lib/api.js` has
  no polling anywhere.

### Suggested fix

Poll while a filing is **signed but has no ticket yet**, and stop the moment it
does. Key it on the filing rather than on `c.status`: `external_ref` is the
thing the viewer is waiting for, and it is exactly what `Live.jsx:255` renders.

```jsx
// Before the `if (!data)` early return at Live.jsx:174 -- hooks cannot follow it.
const pending = Boolean(
  data &&
    !LAPSED.has(data.case.status) &&
    data.filings.some((f) => f.signed_by && !f.external_ref),
)

useEffect(() => {
  if (!pending) return
  const started = Date.now()
  const id = setInterval(() => {
    if (Date.now() - started > 180_000) return clearInterval(id)
    if (document.visibilityState === 'visible') load()
  }, 5000)
  return () => clearInterval(id)
}, [pending, load])
```

**Three details that matter:**

1. **The hook must sit above the early return** at `Live.jsx:174`, so it reads
   `data` directly rather than the `lapsed` computed below it. Put it after
   the return and React throws on the first render that has data.
2. **Cap it.** A desk is *designed* to be unreachable sometimes
   (`unreachable_rate`, 0.10 on vendor). Then the Watchdog pauses the clock and
   retries on a later wake, and the ticket may not come for a long time. Three
   minutes covers the normal ~100s with room; past that, "Read it again" is the
   honest control.
3. **Pause when hidden.** Each poll is a Lambda call against an account capped
   at **10 concurrent executions**, shared with the Watchdog. A forgotten
   background tab should not compete with the filing it is waiting for.

A small touch worth adding while in there: while `pending`, render Ticket as
something like "filing now…" instead of `— none issued —`, so the wait reads as
progress rather than failure.

`MyCases` could use the same treatment, but it matters less — the list is not
where anyone watches a filing land.

## One fault on one street is one case — the cross-case merge (PR #48)

Until this afternoon clustering ran on every claim and **merged nothing**.
`graph/request_path.py` mints a fresh case per report, so twelve households on
one outage opened twelve cases on one feeder; Pattern Watch added each
household to the oldest one and left its own case alive with its own clock,
and the Watchdog filed every one of them separately — the exact duplicate hard
rule 5 warns "reads as spam and gets both copies closed".

Clustering (the score, `TAU`, the window) was already settled. What was never
written was the **merge** rule: which case survives, and what happens to the
other one. That is now in, on `main` at `5cbd705`.

### The rule

- **Survivor = the case furthest along, then the oldest.** Rank is
  `OPEN < DRAFTED < TRACKING < BREACHED < ESCALATING`. A newer case that is
  already tracking a ticket beats an older unsigned draft, because folding
  households into the draft while the filed complaint runs on separately is
  the duplicate this exists to prevent. Oldest is only the tiebreak.
- **The source is absorbed, never deleted.** It goes `WITHDRAWN` with
  `merged_into:<survivor>` in its `merged_from`; the survivor gets
  `absorbed:<source>`. Provenance both ways, in one DynamoDB transaction, so
  `split_case` still reverses it (hard rule 6). Split children are never
  folded straight back.
- **Only the household's OWN case folds**, and only if it is `OPEN` or
  `DRAFTED` with no signed filing. A case holding a ticket stays alive — you
  cannot un-file a complaint — and the trace says so
  (`not_absorbed … a filed complaint cannot be withdrawn`). A case that already
  carries other households is a cluster of its own and is left alone.
- **An absorbed case is not a prior incident.** Its `FEEDER#` index row is
  deleted in the same transaction, so `recurrence_count` on that main does not
  claim eleven earlier failures for one outage.
- **It fires on the CASE insert, not only the claim.** The request path
  writes the claim first and the case seconds later, after Remedy. The first
  version of this merge passed nine tests and would have done nothing live,
  because when the Lambda ran on the claim the household's own case did not
  exist yet. `handlers/ambient.py` now runs the pass on `CASE#…/META` inserts
  too; both passes are idempotent.

### The bug it found on the way: the site never asked for consent

First live attempt on `ward12-8thmain` crossed `TAU` and then logged
`1 household(s) corroborate`. Anti-Abuse refused the join — correctly —
because every web report carried **empty consent**. `handlers/web_api.py`
only forwarded string fields and silently dropped `consent`; the form never
asked. Hard rule 7 says aggregation only with the household's say-so, so the
door now forwards `consent` as a list of known scope names, the client sends
it, and the intake form has an **unticked** checkbox: *"Count my household
with neighbours reporting the same fault."*

**For the demo: tick the box.** Two reports without it will never merge, and
that is the system working, not a bug.

### Verified live, 14 Sep 19:17 IST

Two households on `ward12-1ststage` (`bwssb-tm-16`), both consenting, through
the deployed site:

| | case | after | `merged_from` |
|---|---|---|---|
| A | `case_c12a67495ec0` | `drafted`, corroboration **2**, both households | `absorbed:case_1440b0356d54` |
| B | `case_1440b0356d54` | `withdrawn` | `merged_into:case_c12a67495ec0` |

### Two things to know before you demo it

1. **Pick a quiet street.** The survivor is the furthest-along-then-oldest
   case on the feeder, and the feeder is shared by every test case ever
   reported on that street. On `ward12-8thmain` the first attempt folded the
   new household into a **13 Sep draft** on tm-15 — correct by the rule,
   confusing on stage. `ward12-1ststage` had zero open cases, which is why the
   verification ran there. Check `open_cases` for the street first.
2. **Semantic never ran.** Every merge today is topology + recency,
   renormalised; the trace says `semantic ran on 0/1 pairs` and `UNJUDGED`.
   Say it before a judge asks.
