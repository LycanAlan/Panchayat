### The calibration bug our own hosting introduced

This is the part worth reading.

`Desk` seeds `random.Random(profile.name)`, so every fresh instance replays one
identical sequence. On a laptop that is fine: one long-lived process, and the
sequence advances across filings — which is what the calibrated rates
describe. **A microVM rewinds to roll one on every cold start.**

Deployed, that meant `vendor` and `payments` refused the *first* filing on a
pretext **every single time** — four probes, four identical refusals, where
chance would have made that a 0.24% event. Their published
`reject_malformed_rate` of 0.08 and 0.03 had quietly become **1.0 for the only
filing that matters.** Every calibrated rate in the lane was affected the same
way; those two are simply where the first roll happens to land on a refusal.

This was my bug, in my file. `institutions/desk_store.py` exists precisely so
desk state outlives the microVM, and I did not notice that **the RNG position
is state.** It now checkpoints alongside the tickets, the idempotency map and
the counter. Alakshendra's calibration logic is untouched.

Proven end to end rather than asserted. Before the fix, the rows carried no
`rng` attribute and both desks refused. After: first call still refuses (no
position checkpointed yet), and the second returns `VENDOR-100001` and
`PAYMENTS-100001` because the sequence now resumes instead of replaying.

**Kartik:** this is the one to know about for the tau sweep and any rate you
quote. A rate measured against the deployed desks before today was measuring
the first roll repeatedly, not the distribution.

### Two scripts, because the traps are not memorable

`scripts/deploy_desk.ps1` does configure + launch per desk and prints the ARNs.
It reads `GEMINI_API_KEY` from `.env` so the key is never typed and never
committed — but **it does reach the launch command line**; see the correction
further down. Five traps are closed inside it and written out in
`docs/deploy/SETUP.md` — the entrypoint must sit at the repo root, agent names
take no hyphens, each desk needs its own role, `AWS_PROFILE` must be set, and
on Windows both `uv.exe` and our `zip` shim must be on PATH. A sixth, the
Watchdog Lambda's own packaging, the script never touches and cannot close.

`scripts/smoke_desks.py` files one marked complaint against every deployed desk
and reports what came back. **It retries three times before calling a desk
down**, because every profile carries an `unreachable_rate` and a desk is
*designed* to simulate downtime. Reporting the first `UNREACHABLE` as a broken
deploy is the misdiagnosis that cost us an hour on `bwssb`.

## Read the desk's answer before you call it broken

Two replies look like faults and are not:

- `REJECTED — reference number does not match our records` is `server.py`
  refusing a well-formed filing on a pretext, at the profile's own rate.
- `UNREACHABLE` may be the profile's `unreachable_rate` (0.10 on vendor, the
  highest of the five — a single-operator tanker vendor not answering at 4am).

`agents/watchdog.py` still reports **every** failed submit as "endpoint
unreachable", including a desk that answered clearly and refused. That wording
sent us hunting a network fault for an hour on 13 Sep while the log said
`outcome=REJECTED`. It is Raghav's file and I have not touched it; the message
wants to distinguish "no answer" from "answered no".

## What the code review changed

`/code-review` returned 14 findings on this branch. The ones worth knowing:

**Two microVMs could issue the same ticket number.** `act()` did a
load-modify-write of one shared item per tool call, and AgentCore gives
concurrent filings separate microVMs. Both read `n=5`, both minted
`<DESK>-100006`, and the later `put_item` erased the earlier ticket — two
households holding one reference, one complaint gone from the desk's records.
That is hard rule 5. `save()` is now a conditional write on a `version`
attribute, and `act()` answers a refusal by reloading and re-running. Safe
because `accept()` checks its idempotency key **before** any random draw, so
the loser of a race gets the winner's number back as DUPLICATE.

**A corrupt checkpoint would have killed a desk.** `_restore_rng` caught
`TypeError` and `ValueError`, but `setstate()` raises `OverflowError` for a
negative or oversized word — so a truncated row would have propagated out and
stopped the desk answering anything until someone deleted the row, exactly
contradicting the docstring promising it would still answer.

**The deploy script opened a trap while closing five.** `agentcore configure`
rewrites `default_agent` in `.bedrock_agentcore.yaml`, so after a desk deploy
the next `agentcore` command typed without `--agent` targets a desk instead of
the main runtime. It was left pointing at `panchayat_desk_payments`. The script
now restores it, and the live file is back to `panchayat`. **That file is
gitignored, so nothing would have warned you.**

**A documentation claim I had to withdraw.** I wrote that the deploy script
means the Gemini key "never reaches a command line or a log". That is false —
it is passed to `agentcore launch` as an `-env` argument, so it sits in that
child process's argument vector and in PowerShell script-block logs. It is
protection against *committing* the key, not against a local observer. Corrected
in both the script header and SETUP.md, because a false guarantee is the reason
nobody thinks to rotate.

**And then the fix took all five desks down.** Worth writing down, because the
lesson is about the test and not the code. The conditional write treated "row
exists but has no `version`" as "no row at all", so it conditioned on the row
not existing — against rows that plainly did. Every save raised `Contended`,
`act()` retried three times and re-raised, and all five desks answered nothing.
The smoke test caught it within a minute of the deploy finishing.

**The offline fake had agreed with the bug.** It re-derived the rule from
version arithmetic instead of evaluating the condition `save()` actually
passed, so it agreed with whatever `save()` believed and could not see the one
state that mattered. It now evaluates the real boto3 condition object against
its stored item, which fails the way the deployed desks did. A fake that
re-derives the rule tests only that the code agrees with itself.

A second, quieter one from the same change: PowerShell 5.1's `Set-Content
-Encoding utf8` writes a **BOM**, and a BOM lands inside the first YAML key, so
`default_agent` would have parsed as `\ufeffdefault_agent` and `agentcore`
would have silently stopped seeing the setting the restore exists to protect.
The file is written BOM-free now and the stray BOM is stripped.

**Deferred, with reason.** The reviewer is right that `desk_store` now reaches
into three privates of `Desk` (`_by_key`, `_n`, `_rng`) and that the real fix is
a `checkpoint()`/`restore()` pair on `Desk` itself — so the next attribute added
persists automatically instead of silently failing to survive a cold start the
way `_rng` just did. That is Alakshendra's class and a cross-lane design change,
so it wants a conversation rather than a unilateral edit.
