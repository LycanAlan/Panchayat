A

Why agentic AI at all

The first question, and the one a judge is entitled to be sceptical about. "Could this be a cron job and a form?" deserves a real answer.

A1By design

Why does this need agents rather than a workflow engine and a database?

Because the work is not one process. It is four, running on different triggers, on different timescales, with no shared call stack — and three of them have to make judgement calls with nobody watching.

A form submits a complaint. What this system does is pursue one for eleven weeks: decide which of thirty-one jurisdiction entries fits a sentence someone typed in Kannada; decide whether two households on the same trunk main are reporting one fault or two; decide whether an office that marked a ticket "resolved" actually did anything; decide when a statutory window has breached and who is next up the ladder. Each of those is a decision under ambiguity that has to be made, recorded, and defended with a citation.

The agentic part is not that a model writes prose. It is that each decision is owned by a named component that can refuse — the Remedy agent returns "I do not know, ask" rather than guessing an authority; the Anti-Abuse agent can veto a merge the scorer proposed; the Warden can block a field from crossing the membrane. A workflow engine has no seat for "decline and say why."

Evidencegraph/request_path.py · agents/remedy.py:192 · agents/anti_abuse.py
A2Verified live

What are the four execution paths, and why not model everything as one agent loop?

Because a Graph invocation cannot wait seven days, and it cannot react to a row arriving. Exactly one of the four things this system does is request-scoped.

Forcing the deadline-chasing into the request path is the mistake that makes this product a chatbot: the household closes the tab and the eleven-week pursuit — the entire premise — stops.

EvidenceCLAUDE.md §"four execution paths" · handlers/temporal.py · handlers/ambient.py
A3By design

Why A2A between the institutions instead of one bigger Swarm?

Because a Strands Swarm maintains a mutable SharedContext that every agent in it reads and writes. That is correct inside one household and catastrophic across households.

Putting BWSSB's desk and five households in one Swarm would mean every participant can read every other participant's state. The privacy promise would be decorative. So the trust boundary is a process boundary: the institution desks never import core.store and have no access to our table. They hold their own tickets in their own memory, exactly as a real office would.

Same argument at the other end: the Swarm is used inside one household, where members legitimately share context when deciding what the household wants.

Evidenceinstitutions/server.py:6–10 · agents/household.py:45 · CLAUDE.md §Verified API surface
A4By design

Clustering is the headline. Why is it not part of the request path?

Because the spine has to work at N=1, and clustering must never gate a single household's complaint.

One household reporting alone gets the full journey: routed, drafted, tracked, escalated. Clustering is ambient — it watches claims arriving behind that and upgrades a case already in flight when a pattern crosses threshold. Nobody opts in to collective action; it happens to them and then they are told.

The consequence worth stating on camera: on a quiet street this system invokes no model for weeks. That is a feature of the design, not an outage.

Evidencehandlers/ambient.py:14–18 · agents/pattern_watch.py
A5Verified live

Isn't the "Graph" just a state machine with LLM flavouring?

Partly, and deliberately. Several spine nodes must never call a model, and the code says so in the type.

FunctionNode wraps a plain Python callable as a Strands graph node. warden.minimise() is field reduction — a model there could improvise a leak. remedy.resolve() is a table lookup — a model there would hallucinate an authority. Nodes that genuinely reason, like intake extraction and household deliberation, take a real Strands Agent, and add_node accepts either.

The honest framing: this is a graph where the reasoning is concentrated where ambiguity actually lives, and everything else is deterministic and auditable. A judge should be more worried about the reverse.

A6Verified live

How many agents are there, exactly?

Eight: intake, household, warden, remedy, watchdog, pattern_watch, anti_abuse, digest. Plus five institution desks on the far side of the A2A boundary, in their own processes.

Our own docs used to disagree — README.md claimed eleven, CLAUDE.md claimed nine, and core/tags.py claimed eleven again. All three now say eight, which is what a judge who counts files will find. The household Swarm additionally spawns one Agent per member at runtime, which is where the inflated counts came from.

The same pass fixed a larger overclaim: the README said "all five Strands multi-agent patterns", and Workflow is never imported anywhere in the repo. Four are genuinely used — Swarm, Graph, Agents-as-Tools, A2A — and the escalation ladder is our own class driven by the Watchdog across weeks, because no Workflow invocation survives a seven-day statutory window.

B

Where the model actually runs

The uncomfortable one. Bedrock's data plane is blocked on this account, so be precise about what that costs and what it does not.

B1Account-blocked

Bedrock is blocked. So is there any AI running in this at all?

Right now the deployed spine completes with totalTokens: 0. Every node that would call a model falls back to deterministic parsing instead. That costs quality, not availability — and we say so rather than hiding it.

Every bedrock-runtime invoke on this account returns ValidationException: Operation not allowed, all vendors, all regions, while the control plane happily lists 120 models. It is account-level authorization — not IAM, not model access, and nothing in the console fixes it. Support case 178898467100367.

Read the error, it tells you which problem you have. AccessDeniedException names a principal and means an IAM policy is missing, which you can fix. ValidationException: Operation not allowed names the account and you cannot. Conflating the two cost us a day.

What is not blocked

AgentCore itself. Runtime, Memory, Gateway, Identity and Code Interpreter all answer clean — which is the part the hackathon actually grades. The deploy target was never at risk.

EvidenceCLAUDE.md §Bedrock · core/models.py:110 probe() · docs/DEPLOY.md:236
B2By design

So which steps would call a model, and which never will?

Four call sites, all injectable. Everything else is a lookup or a comparison, permanently.

  • Intake extraction — only when one sentence carries more than one problem. A single-need report needs no model at all; the split is deterministic on and / ; first.
  • Household deliberation — the Swarm, deciding what this household actually wants.
  • Pattern Watch adjudication — the one model call in the mesh lane: are these genuinely the same failure?
  • Embeddings — Titan v2, in the ambient Lambda, on the stream record.

Never: the Warden (a model could improvise a leak), the Remedy lookup (a model would invent an authority), and the whole of Anti-Abuse — "no model in this file, ever. The text this agent polices is household-authored, and a model reading it could be talked into approving the merge by the very thing it is meant to catch."

Evidenceagents/intake.py:52 · agents/pattern_watch.py:291 _judge() · agents/anti_abuse.py:12 · core/scoring.py:254 embed()
B3By design

Why is the model never allowed to pick the authority?

Because a hallucinated authority reproduces the exact failure we claim to fix.

Filing against the wrong department is the most common way a valid complaint quietly dies — and the citizen is never told that is what happened, only that the ticket closed. A model that invents "BBMP Water Department" would be manufacturing precisely that outcome while looking confident.

So the division of labour is explicit: a model may read messy free text well enough to pick the key — service, segment, feeder. It may never produce the value. The authority comes from data/jurisdiction/*.yaml or the agent says it does not know and asks. Every routing decision carries a citation, and an entry with no statute_ref raises at load: "an entry without a citation is a guess with a table around it."

Evidenceagents/remedy.py:1–17 · agents/remedy.py:108 (statute_ref guard) · hard rule 3
B4By design

Which models, which region — and why is our data in India but the inference in the US?

Because ap-south-1 has no Anthropic inference profiles at all. The table and the runtime are in-country; the model calls are not, and never were.

Two seams make this survivable: PANCHAYAT_MODEL=bedrock|anthropic swaps the entire provider with an environment variable, so when authorization clears you change a variable rather than eight agent files. Paying Sonnet prices to classify a complaint is silly, hence two roles.

Evidencecore/models.py:44–56 · STATUS.md:269
B5By design

No embeddings means no semantic similarity. Doesn't clustering just break?

It would have, silently, and finding that out was the most valuable half-day of the build. A missing embedding means the semantic term is unavailable, not zero.

The weights are topology 0.40, recency 0.25, semantic 0.35, against TAU = 0.72. Score a missing embedding as zero and the ceiling becomes 0.40 + 0.25 = 0.65 — below threshold. Two houses on one trunk main reporting the same fault a minute apart would score a perfect 1.0 on both components that actually ran and still never cluster. Nothing errors, nothing logs; Pattern Watch just never fires.

So the term is dropped and the score renormalised over the weights that did run. It degrades safely in the right direction too: the decoy on a different feeder scores topology 0, so its renormalised ceiling is 0.385 and it still does not cluster.

Say this out loud in the demo

CorrelationScore.semantic_available must reach the trace UI. While Bedrock is blocked, every cluster forms this way. Showing clusters without saying semantic never ran is claiming agreement the system did not compute.

C

Who receives the complaint

Nothing is autonomous about this. Follow one report from a sentence to a named officer's desk and see where the human sits.

C1Verified live

Who actually receives the complaint, and how does it get there?

A named officer at a specific tier — "BWSSB Assistant Engineer, sub-division office", not "BWSSB" — reached over A2A through a desk that is deliberately a separate process from ours.

household POSTs  → AgentCore Runtime, /invocations
intake          → 1 need parsed from the text
household       → what this household actually wants
warden          → a Claim crosses the membrane. Nothing else does.
remedy          → looked up: BWSSB (not BBMP)  [BWSSB Citizen Charter]
file            → DRAFTED to the Assistant Engineer, tier 1
                   — awaiting a human signature —
watchdog        → SLA 7d, EventBridge wake booked for the breach date
a person signs  → approve(idempotency_key, member_id)
climb()         → InstitutionClient → A2A desk → ticket reference back

Addressing the tier's officer rather than the umbrella body is most of what makes a filing land — and it is also load-bearing in code, because Filing.compute_key() hashes case_id|authority|tier. If the Watchdog computed that key from the ladder step and the request path computed it from the umbrella body, the two keys would differ, duplicate suppression would fail, and the same complaint would be filed twice.

Evidencegraph/request_path.py:454 _file() · institutions/routing.yaml · institutions/client.py:292 build_submit()
C2Verified live

Does the system file complaints by itself?

No. Hard rule 4: agents draft, humans sign. No filing against a public body is submitted without a named person approving it, and that is enforced in the deployed system, not just in tests.

The signature takes a member_id and explicitly not a household — "the liability lands on a person, and 'the household agreed' is not a signature anyone can be held to." Approving does not submit either: recording approval and handing paper to an institution are two different acts, and collapsing them would put a network call behind a click.

Verified on the live endpoint: approve recorded mem_001; approving a second time was refused with the original signatory left intact. In the live table right now, three filings sit under the UNSIGNED partition and one does not — that one is the filing a human signed.

C4Verified live

What happens when nobody answers, or the office closes it falsely?

The Watchdog wakes on the breach date, disputes a false closure using corroborating evidence, and climbs the ladder. Four tiers, each with its own statutory window and citation.

Tier 2 is where corroboration earns its keep — "reopen with contradicting evidence; corroborated household count matters here." One household saying the tap is dry is deniable. Seven households on one trunk main, timestamped, is not.

Evidencedata/jurisdiction/ward12.yaml ladders · agents/watchdog.py:311 reconcile_closure() · :445 climb()
C5Verified live

If a Lambda retries, does the household get filed twice?

No. Hard rule 5: every institutional action is idempotent. A retrying Watchdog that files twice produces a duplicate that reads as spam and gets both copies closed.

put_filing_once() writes under a key hashed from case_id|authority|tier with a conditional put; a second identical filing is recorded as DUPLICATE in the trace rather than sent. The two Lambda paths also have deliberately opposite retry semantics, which is the subtle part:

  • Temporal must raise on a retryable failure — EventBridge deletes the schedule when the Lambda returns cleanly, so returning a tidy error destroys the case's only pending wake.
  • Ambient must not raise — a DynamoDB stream retries the whole batch from the same position, so one poison record would block every later claim on that shard for 24 hours. It returns batchItemFailures instead.

D

Grounding without real location data

No GPS, no household registry, no address database. So how does a sentence become a named officer at a named office?

D1Verified live

There is no location service. How is the jurisdiction query resolved?

By a segment — a curated street-level key that arrives in the request payload — matched against a hand-curated table. It is a lookup against 31 rows, not a geocode and not a guess.

lookup(service=water, segment="ward12-4thcross", feeder_id="bwssb-tm-14")
  → authority     BWSSB        not_authority  [BBMP]
    feeder_id     bwssb-tm-14   sla_days       7
    statute_ref   "BWSSB Citizen Charter, restoration of interrupted supply"
    helpline      1915

Free text reaches that key through 74 curated aliases — how people actually write a street: "4th cross", "4th cross road", "fourth cross". The aliases live in the same YAML as the data rather than in a second copy that drifts.

Three things this does that a geocoder would not. A miss returns None and the system asks rather than guessing. A caller-supplied feeder_id that contradicts the curated one is treated as a miss too — "rather than filing against a body chosen by whichever of the two we happened to trust." And lookup() returns a deep copy, because a caller that mutated the shared table would empty a ladder and stall climb() on every later case, invisibly.

Evidenceagents/remedy.py:165 lookup() · data/jurisdiction/ward12.yaml · 31 entries, 74 aliases, 9 feeders
D2Known gap

Where does segment come from, then? Isn't that passing the buck?

It has to arrive with the request, because there is no household registry — nothing in the repo writes a Household row. This is a real gap and it is documented in the entrypoint rather than hidden.

HouseholdPosition is frozen and carries no segment; jurisdiction is looked up by segment; so the caller must supply it. When it is missing, the response says unrouted_reason: "no_segment" rather than failing quietly five nodes in. An earlier version of the entrypoint docstring omitted segment from the payload example — which is how a deployed endpoint would have answered every real report with UNROUTED while looking perfectly healthy.

In production this is where an address-to-segment service or a one-time household registration sits. In a five-day build it is a field in the payload, said out loud.

D4By design

Why does feeder_id matter so much?

Because it is what separates "the same fault" from "two faults on the same day", and it cannot be recovered after the fact.

The topology score is 1.0 for a shared trunk main and 0.15 for an adjacent segment on a different one. Two houses fifty metres apart on different feeders are not the same fault; two houses four hundred metres apart on one trunk main are. Distance is the intuitive signal and it is the wrong one. There are 9 feeders across the 31 segments, so the table can express both cases.

Evidencedata/jurisdiction/ward12.yaml:52–60 · core/scoring.py W_TOPOLOGY
D5Synthetic

Is the complaint corpus real complaints?

No — it is synthetic, and the important property is that it is blind to the scorer. A test asserts that against the source, because an import added later would silently invalidate every number the corpus produces.

It models the failure first and the claims second: pick a feeder → decide it fails → decide who notices → decide who bothers to report → emit claims. Roughly 25–40% of affected households end up filing anything.

That funnel is not incidental realism — it is the premise of the project. A corpus where everyone complains is measuring a world where the problem has already been solved, and any density curve drawn against it would flatter the system by exactly the amount that matters. Fault.affected is recorded alongside Fault.claims so the curve can ask the real question rather than the flattering "of those who complained".

E

What is hard-coded, and what the tests actually prove

The sharpest version of this question is "could you have faked all of this?" Here is what the suite catches and, more usefully, what it does not.

E1Verified live

Is everything hard-coded?

Three different things get called "hard-coded" and only one of them is a criticism. Worth separating them.

  • Curated data — the 31 jurisdiction entries, the ladders, the aliases. Hard-coded on purpose: this is the one thing a model is forbidden to generate.
  • Calibrated parameters — TAU = 0.72, the weights, the desk failure rates. Not guessed: TAU is swept by eval/tau_sweep.py, and the comment in the source says "do not hardcode a defended number."
  • Deterministic fallbacks — the canned results nodes return while Bedrock is blocked. These are the honest weak point, and they are marked stubbed=True in the trace so the demo surface says so out loud.

What is emphatically not hard-coded: the routing decision, the case state machine, the escalation tier, the SLA arithmetic, the idempotency keys, the storage layout. There is no if demo_mode: anywhere in the repo, and adding one to the Watchdog is explicitly forbidden by hard rule 1.

Evidencegraph/request_path.py:81 run_or_stub() · graph/trace.py Transition.stubbed · core/scoring.py:31
E2By design

What does run_or_stub catch, and why only that?

It catches NotImplementedError and nothing else, on purpose. A real bug in a teammate's code must surface as a failure rather than get papered over by canned data that makes the demo look fine.

It is one helper rather than the same try/except at every node, because four copies of the protocol is four chances to forget the stubbed marker — and a trace that under-reports its own stubs is worse than no marker at all. As lanes land, their stub markers disappear one by one; nothing gets rewired.

The same discipline shows up in two other places worth pointing at: the scheduler raises a specific SchedulerNotConfigured so callers can degrade on exactly that and a genuine outage still raises; and when no wake gets booked the trace prints NO WAKE SCHEDULED rather than a confident TRACKING line — "the most expensive lie this system could tell a household."

Evidencegraph/request_path.py:81 · core/clock.py:54 · graph/request_path.py:536

The same tests run against both storage backends. What does that catch?

Divergence between the thing we develop against and the thing we ship. The rule is that if a test passes on memory and fails on DynamoDB, the DynamoDB one is wrong — and we find that out on our own bench rather than during integration.

It has already caught a real one. The seam originally had an OPTIONAL list, and stalled_cases lived on the memory backend alone for a day: the queue that surfaces a stuck household to a person worked offline and nowhere else, and nothing failed until somebody ran the suite against a real engine. E6Synthetic

What does the eval harness measure — and what does it deliberately not?

Routing accuracy against 50 labelled complaints, with a target of 80%. It measures the table's coverage. It does not yet measure the extraction, and the file says so in its own header.

The default extractor is keyword matching over the curated aliases, and the corpus was hand-labelled by the same person on the same afternoon — so a high score says the table is wide enough, not that the NLU works. evaluate() takes the extractor as an argument precisely so the real model call swaps in on one line and the number starts meaning the harder thing.

Three complaints in the set are written the way people actually write them — abbreviated, misspelt, unspaced — and the alias list does not cover them. They are labelled with the true authority and count as failures: a gate that cannot fail is not a gate.

Evidenceeval/routing_accuracy.py:1–24 · eval/tau_sweep.py · eval/density_curve.py
E7By design

Time is compressed for the demo. Isn't that simulating away the hard part?

It would be, if the compressed path were different code. The rule that keeps it honest: both clock implementations drive the same Watchdog function.

TIME_SCALE=1 is production; TIME_SCALE=86400 makes one statutory day elapse in one real second. Seven statutory days cannot elapse inside a five-day build, so the Watchdog has to be able to run on compressed time — but there is no if demo_mode: branch inside it, and adding one is forbidden. "If you want to, the clock is wrong."

Hard rule 1 is enforced by the linter, not by memory: DTZ is in the pinned ruff selection, so datetime.utcnow() fails the build. The institution desks import the same clock too — an office answering on wall time while the Watchdog runs at 86400× would never respond inside a window, and the demo would be measuring nothing. Shared time is not shared state.

Where the output is stored

One table, six row types, in India. Plus traces, and one place where nothing durable is written yet.

F1Verified live

Where does everything actually get stored?

A single DynamoDB table named panchayat in ap-south-2 (Hyderabad), single-table design, PK/SK with one GSI. It holds 28 rows right now from real invocations of the deployed endpoint.

The FEEDER# rows exist because the declared case index is keyed on status, so there is no index on feeder_id at all. Without them, "who else is on this feeder" would be a full scan on the ambient path.

F2Verified live

Is the data in India?

The table and the runtime are both in ap-south-2, Hyderabad. The model calls are not, and never were — ap-south-1 has no Anthropic inference profiles at all.

Worth knowing why we are in Hyderabad rather than Mumbai: the AgentCore maxAgents quota is per-region, and it is 0 in us-east-1, us-west-2, eu-west-1 and ap-south-1, while sitting at the full default of 1,000 in ap-south-2. Four zeroed regions were nearly generalised to "all of them", which would have meant waiting on a support ticket that did not need to exist. Data residency is a happy side effect of that, not the original reason.

Evidencearn:aws:bedrock-agentcore:ap-south-2:699073937307:runtime/panchayat-3FFhtr5OfG
F3Verified live

Where do the traces go, and can you actually follow one case?

CloudWatch, and yes. AgentCore instruments the runtime itself — our panchayat log lines already arrive with otelTraceID set and otelTraceSampled: true.

Every node opens a span carrying its case_id, so every span from one case, across all four execution paths, sits under one query. Without it a slow request is just a slow request; with it, the node that cost the time is named.

The CaseTrace object is separate and more important for the demo: it is the human-readable story, and it is treated as a first-class product surface rather than a log. Almost nothing good about this system has a natural screen — the Warden refusing to leak an inference, Pattern Watch going four days without invoking a model, the Watchdog disputing a closure using seven other households' claims. All of it happens in a log, so the log is the product.

Known gap

demo/trace_ui/ is an empty untracked folder. The data is all there; nothing renders it yet.

Evidencegraph/trace.py:1–14 · graph/nodes.py:68–74 · graph/observability.py
F4By design

What runs when nothing is happening?

Nothing. There is no poller, no scheduled sweep, no always-on process.

A wake is booked against a specific case for a specific date as an EventBridge schedule named pnc-<case_id>-<action>, with ActionAfterCompletion: DELETE so it cleans itself up. The Watchdog is stateless between wakes — AgentCore Runtime sessions cap at eight hours and statutory windows are measured in weeks, so all case state lives in the table and nothing is held in memory across a deadline.

On a quiet street the ambient path invokes no model for weeks, the temporal path sleeps until a real date, and the cost is storage plus the requests that actually arrive.

G

Privacy, safety, and the limits we will say out loud

The questions where the right answer is sometimes "that is a real hole, here is where it is."

G1By design

What crosses the privacy membrane, and what never does?

Only a Claim crosses, and only the Warden emits one. HouseholdPosition — the thing that knows what the household actually wants and why — never leaves.

The Warden also scans for correlation leaks, which is the class no schema catches. A household declining Tuesday and Friday swaps has told the mesh someone has a Tuesday–Friday commitment; the leak is in the pattern, not in any single field.

The read API applies the same discipline outward: get_case and list_cases build responses from an allowlist projection, not by deleting fields from the full object. That is not stylistic — a denylist means every new field on Case is published by default until someone remembers to redact it.

Two leaks this caught in our own code

Why "minimisation, not anonymity"? Why not just promise anonymity?

Because it would be a lie, and a checkable one. Eight houses on a cross street means any claim precise enough to file is precise enough to identify.

A complaint that says "no water on 4th Cross for three days" against a feeder with nine households on it is not anonymous no matter what we do to the payload. What we can actually guarantee is that income, health, arrears and schooling never cross the membrane — and that is a promise the code keeps rather than a claim the marketing makes.

G3By design

Could this be turned against a neighbour?

Aggregation points outward only. Collective pressure may be assembled against an institution, never against a person or a household — and that rule is in the routing data, not only in the README.

The escalation ladder for a private layout has the residents' welfare association at tier 2, and the A2A routing table gives it no desk, with the reason stated in the file: "the RWA is a neighbour, not an institution." Same for the layout developer: "contractual, not statutory — this tier is a conversation the household has to have." Those are guardrails, not missing integrations, and the Digest surfaces them to a person instead.

And nothing here touches the police. Read, track, advise only — no autonomous FIR filing, in any tier, for any service.

G4Known gap

Anyone can call approve with any member_id. Isn't that a hole?

Yes. It is the single largest gap in the deployed system and we should name it before a judge does.

There is no authentication on the endpoint. Anyone who can invoke it can read any case by id and approve any filing by passing any member_id string. Hard rule 4's "the liability lands on a named person" is currently only as strong as the caller's honesty.

The frontend team must know this: a UI that lets someone type their own member_id makes the signature meaningless. The fix is an identity layer — AgentCore Identity exists for exactly this — and it is P1.
